# 販売準備：参加制限とTURNの設定

基準：main `66ffd6564bb3202a6c3b54d19de8e352098990e2`、Android 0.2.4。追加実装は別ブランチで検証する。本番は変更していない。

## 互換性と移行

設定なしでは従来の店舗IDなし・ルームIDだけの参加を維持する。店舗IDを入力した参加は、対応するポリシーがなければ拒否する。公開ルームと制限ルームは名前空間が別なので、同じルームIDでも相互に参加・信号中継できない。

旧APKは新サーバーの従来ルームに参加できるが、店舗参加・TURN設定の取得には更新クライアントが必要。新クライアントは旧サーバーでも従来ルームを利用できる。旧サーバーは店舗IDを検証しないため、新クライアントは `server-capabilities` の参加制限プロトコルを確認してから店舗参加を送る。未対応サーバーでは5秒後に参加を中止し、招待コードを送らない。販売用クライアントは、更新サーバーと組み合わせて使う。

販売用は別の検証サーバーで `ALLOW_LEGACY_ROOMS=false` にして、店舗なしの参加を禁止する。店舗IDだけ公開しても入れない。従来ルームを有効なまま残して「全ルーム保護済み」と案内しない。旧利用者を閉じたルームへ移すのは、更新・招待の配布・実機確認後。

Androidの接続先は標準では既存Render URL。検証先はビルド時の `INTERCOM_SERVER_URL=https://検証ホスト` で切り替えられる。TLSが必須。アプリIDと音声・通話ボタン処理は変えない。デバッグAPKは販売・上書き配布用ではない。署名鍵を新規作成・公開しない。

## 招待の作成

リポジトリ外の非公開フォルダで生成する（例の有効期限は実運用に合わせて変える）。

```sh
node scripts/create-invite.js /private/backups/shop-invite.json 2027-01-01T00:00:00Z
```

256bitの乱数コードと、SHA256ハッシュ・UTC有効期限を含むJSONを0600で新規保存する。コードは標準出力に出さない。既存ファイルを上書きしない。秘密ファイルをGitや共有ログへ載せない。参加者には `inviteCode` と店舗ID・ルームIDを安全な別経路で配布する。今回は配布していない。

ホストの秘密環境変数 `ACCESS_POLICY_JSON` に下記構造を設定する。ハッシュは生成ファイルの `rule.sha256` を使用。下記の文字列は構造説明用で、動作する値ではない。

```json
{
  "shopA": {
    "rooms": {
      "kitchen": {
        "maxParticipants": 10,
        "invites": [
          {"sha256": "生成した64文字の小文字16進ハッシュ", "expiresAt": "2027-01-01T00:00:00Z"}
        ]
      }
    }
  }
}
```

店舗ID・ルームIDは半角英数字、_、-で1〜32文字。制限ルームの定員は1〜50。招待は複数登録できる。`invites: []` は閉鎖。設定の構造不正は値をログに出さず起動拒否する。.envは自動読込しないため、実行環境から明示的に渡す。`.env.example` に実秘密を記入・コミットしない。

参加時にコードを照合し、期限と定員も検証する。サーバーは同一ルーム参加者だけへ信号を中継。認可前は参加者一覧・TURN認証情報を返さない。参加済みでも期限を1秒間隔で確認し、退出を通知する。正規クライアントはマイク・接続・ボタン操作を終了する。名前は同室へ表示するので、本名必須ではない。

招待の削除・更新は秘密設定を変更してサーバー再起動する運用。この実行では行っていない。再起動時は接続が切れ、再参加検証が走る。コードは共有可能な所持者認証であり、本人確認・購入確認・一度限りの招待ではない。個別コードを発行すれば個別に取り消せるが、コードの共有そのものは防げない。

## TURN

coturnのTURN REST認証互換方式を使う。未設定は既存のGoogle STUN 2件のみ。静的なTURNパスワードをAPKに埋め込まない。

| 環境変数 | 内容 |
|---|---|
| TURN_URLS | JSON文字列配列。例 `["turn:relay.example:3478?transport=udp","turns:relay.example:5349?transport=tcp"]` |
| TURN_SHARED_SECRET | coturnと同じ非公開の32文字以上の共有秘密。公開せずホスト秘密設定へ登録 |
| TURN_CREDENTIAL_TTL | 1200〜86400秒、既定3600秒 |
| ALLOW_LEGACY_ROOMS | 既定true。販売サービスはfalse |
| ACCESS_POLICY_JSON | 店舗・ルーム・招待ハッシュ・UTC期限・定員 |

URLと秘密はセットで指定する。不一致なら起動拒否。coturn側は `use-auth-secret`、`static-auth-secret`、`realm`、TLS証明書と公開IP、通信ポート／リレーポート範囲を用意する。設定の詳細は [coturn公式](https://github.com/coturn/coturn/wiki/turnserver) を参照。プロバイダー方式が異なる場合は、このコードをそのまま適用できない。

参加を認めたSocketへ `rtc-config` を送った後、`existing-users` を送る。usernameは期限付き、credentialは共有秘密によるHMAC-SHA1のbase64。共有秘密は端末へ渡さない。Android・Webは受領したICE設定でPeerConnectionを作成。10分ごとに再取得し、既存接続の設定も更新する。サーバーは再取得時も認可を確認する。

TURNは現在未契約・未接続。DNS・有効なTLS証明書・NTP時刻同期・UDP/TCP/TLSの疎通・中継帯域料金を契約前に確認する。RenderのHTTPサービスに設定を書くだけでTURN中継サーバーになるわけではない。

## 制約と運用

- ルームはプロセス内メモリ。単一インスタンスで運用する。水平分割には共有ルーム管理・Socket.IO adapter・認可状態同期が別途必要。
- 入室試行は接続ごとに10回/分。高エントロピーコードが前提。販売前に入口でIP単位の接続・試行レート制限と同時接続上限を設定し、負荷試験する。再接続による試行回避を現方式だけで防げるとは主張しない。
- WebRTCは端末間通信。サーバーの認可は接続調整の境界であり、不正改造クライアント間で既に確立された直接通信を強制停止する仕組みではない。発行済みTURN資格情報も期限までは使える。厳密な即時失効・人数制御が必要ならSFU等の設計検討が必要。
- サーバー／SDK／プロキシの詳細ログに招待、TURN資格情報、SDP、ICEを出さない。TLSと秘密設定のアクセス権、委託先ログ保持も確認する。アプリ独自の接続エラーログは機密値を含まない固定文に変更した。
- 販売用本人・購入認証、セルフサービス店舗管理、永続DB、購入ライセンス検証は未実装。今回の招待は運営者が発行する参加制限。
